# 19 - Transport Security

**Project:** TivuStream Privacy Intelligence Engine (PIE)

**Document:** Transport Security Specification

**Version:** 1.0.2

**Status:** Approved

**Last Updated:** 2026-09-30

---

# Purpose

This specification defines **how PIE is reached from another device on the
network, over an encrypted connection**.

It was written when the interface opened only on the computer PIE runs on. The
Authentication Specification refuses any password travelling in the clear
outside the loopback, and no encrypted connection existed, so there was no way
in from a phone or another computer in the house. It was the largest limit on
using the project, and the Beta criterion that was missing: "the interface is
reachable over HTTPS". The milestones below are implemented.

The specification does not change the rules of the Authentication
Specification about credentials: it makes them usable outside the loopback.

---

# Threat Model

The adversaries are those of the Authentication Specification. Here the first
matters most: **another device on the network**, observing the traffic or
pretending to be PIE.

| Threat | What is to be prevented |
| --- | --- |
| Listening on the local network | Reading passwords, session cookies and network data in transit |
| A device pretending to be PIE | Collecting the password of someone who believes they are talking to PIE |
| A badly configured proxy in front of PIE | Passing off as local, and therefore accepting, a password that arrived in the clear |

**Not considered, and declared:** whoever controls the network **before** a
device connects for the first time and presents a certificate of their own.
With a certificate generated by PIE, the protection against this attack is the
comparison of the fingerprint, which is up to the person (see Known Limits).

---

# Principles

1. **It works without external services.** No public certificate authority, no
   domain, no connection to the internet. That is Local First.
2. **It works without configuration.** A new installation is reachable over
   HTTPS from the local network without anyone writing a file.
3. **Whoever has better, uses it.** A certificate of one's own, or a proxy
   terminating the encrypted connection, replaces the generated one.
4. **The compromise is declared.** A locally generated certificate makes the
   browser show a warning. It is stated, how to verify it is explained, it is
   not hidden.
5. **A password never travels in the clear outside the loopback**, not even
   through a proxy.

---

# Scope

**It covers.**

* the interface served by the engine, on the same address as the API;
* the certificate PIE generates, how it is kept and how it is renewed;
* a certificate supplied by the operator;
* a proxy terminating the encrypted connection in front of PIE;
* the addresses PIE listens on and the names it accepts.

**It does not cover.**

* **Certificates from a public authority** (Let's Encrypt and the like). They
  require a domain and a connection to the internet. Whoever has them supplies
  them as a certificate of their own.
* **The installation procedure**, which uses what is defined here
  (Installation Specification).
* **Access from outside the house.** PIE is meant for the local network.
  Exposing it to the internet is the operator's choice, outside this
  specification.

---

# The Interface Served By The Engine

**The engine serves the compiled interface**, on the same address and the same
port as the API:

* `/api/...` is the API. An unknown `/api` address answers `404` in the common
  structure, never with the page of the interface.
* Every other address receives the files of the interface, and an address that
  matches no file receives `index.html`, because the routes of the interface
  (`/domains/...`) exist only in the browser.
* The compiled files of the interface live in the `wwwroot` folder of the
  engine, produced by the build and not versioned.

A single address means a single certificate, no rules between different
origins, and the protection on `Origin` of the Authentication Specification
carrying on working as it is.

In development nothing changes: `npm run dev` with the proxy towards the
engine.

---

# Listening

| Channel | Addresses | Default port | Purpose |
| --- | --- | --- | --- |
| HTTP | **loopback only** | `5000` | This computer and development |
| HTTPS | **every interface** | `5443` | The other devices on the network |

HTTP stays on the loopback alone: from another device it cannot be reached, so
there is no address in the clear from which to attempt a sign in.

Whoever does not want PIE reachable from the network sets
`Transport:HttpsPort` to `0`: the HTTPS channel does not open, and only the
local one remains.

The first time the HTTPS channel opens, Windows asks whether to allow incoming
connections. The installation procedure explains this.

# Certificate

## Generated By PIE

When the operator supplies no certificate, **PIE generates one** at first
start.

| Property | Value |
| --- | --- |
| Algorithm | ECDSA P-256 |
| Validity | 397 days, the maximum every browser accepts |
| Names | `localhost`, `127.0.0.1`, `::1`, the name of the computer, and the addresses of its active network interfaces, plus the names listed in `Transport:Names` |
| Use | Server authentication only. It cannot sign other certificates |
| Kept in | `data/tls/`, private key readable only by the user running PIE |

**It is not a certificate authority**, and is not to be installed as one. A
local authority would avoid the warnings, but its private key could sign a
certificate for any site at all, and whoever obtained it would read the
traffic of every device that trusts it (see Decisions Taken, S1).

**Renewal.** At startup PIE generates a new certificate when fewer than 30
days remain before expiry, or when the names and addresses of the computer are
no longer those in the certificate: an address changed by the router would
make the certificate invalid for the name it is reached by. A new certificate
makes the browser warning reappear, once per device.

**Fingerprint.** At startup PIE writes to the output and to the log the
SHA-256 fingerprint of the certificate in use, and the HTTPS addresses it can
be reached at. The fingerprint is not a secret. It is what the person compares
with the one the browser shows, to know they are talking to their own PIE.

## Provided By The Operator

`Transport:Certificate:Path` points at a certificate of one's own, in PFX
format (with `Transport:Certificate:Password`) or PEM (with
`Transport:Certificate:KeyPath`). When it is set, PIE generates nothing and
renews nothing.

A certificate that is set but unreadable, expired or without a key **prevents
startup**, with a message saying why. Falling back silently on a generated
certificate would change the fingerprint under the person's eyes without
telling them.

The password of the certificate, like every credential, lives only in
`appsettings.Local.json`.

---

# Names Accepted

The Authentication Specification limits the names PIE answers to
(`AllowedHosts`) to the names of the loopback alone, against DNS rebinding.
From another device PIE is reached by the name or the address of the computer.

**The names accepted therefore include those of the certificate**: the
loopback, the name of the computer, the addresses of its interfaces, and
whatever `AllowedHosts` or `Transport:Names` add. `*` still prevents startup.

The protection against DNS rebinding stays intact: the attack uses the name of
a malicious site pointing at the local address, and that name is not among
those accepted. The addresses and the name of the computer are not names an
external site can put in the `Host` header of the victim's browser.

---

# Strict Transport Security

The Authentication Specification asks for `Strict-Transport-Security` on every
encrypted connection. **With a certificate generated by PIE it must not be
sent.**

A browser that has received HSTS for a name no longer allows a certificate
warning for that name to be accepted. At the first renewal, or at a changed
address, PIE would become unreachable from that device with nothing the person
could do short of clearing the browser data.

HSTS is sent **only with a certificate supplied by the operator**, which is
presumed to be recognised by browsers. Behind a proxy, HSTS is the proxy's
business.

---

# Behind A Proxy

A proxy that terminates the encrypted connection and forwards to PIE in the
clear on the same machine makes every request arrive from the loopback.
Without further rules, PIE would accept as local a password that travelled in
the clear from the phone to the proxy, if the proxy is configured in the
clear.

* `Transport:TrustedProxies` lists the addresses of the proxies PIE trusts.
  Only from those addresses does PIE read `X-Forwarded-For` and
  `X-Forwarded-Proto`: the address of the client and the encryption are the
  ones the proxy declares, and the rules of the Authentication Specification
  apply to those.
* A trusted proxy must use `X-Forwarded-For` and `X-Forwarded-Proto`. The
  standard `Forwarded` header is not read: a request carrying only that one
  keeps the address of the proxy and falls under the rule below.
* Declaring a proxy makes nothing else trusted. In particular the loopback,
  which the framework treats as trusted by default, is trusted only if it is
  listed.
* **A request from the loopback carrying a forwarding header**
  (`X-Forwarded-For`, `X-Forwarded-Proto` or `Forwarded`), when no proxy is
  declared trusted, **is not treated as local**: a password receives
  `TransportNotSecure`. A browser on this computer never sends those headers.
  Whoever sends them is a proxy, and an undeclared proxy is not a reason to
  trust.

# Configuration

| Key | Default | Meaning |
| --- | --- | --- |
| `Transport:HttpPort` | `5000` | HTTP port, on the loopback alone |
| `Transport:HttpsPort` | `5443` | HTTPS port on every interface. `0` closes it |
| `Transport:CertificateDirectory` | `data/tls` | Where PIE keeps the certificate it generates |
| `Transport:Names` | empty | Additional names, in the generated certificate and among those accepted |
| `Transport:Certificate:Path` | empty | A certificate of one's own, PFX or PEM |
| `Transport:Certificate:KeyPath` | empty | Key of the PEM certificate |
| `Transport:Certificate:Password` | empty | Password of the PFX certificate, only in `appsettings.Local.json` |
| `Transport:TrustedProxies` | empty | Addresses of the trusted proxies |

# What The Person Sees

**At startup**, in the output:

```text
PIE is reachable at:
  https://Buietto-PC:5443
  https://192.168.1.5:5443
Certificate generated by PIE, valid until 2027-10-28.
SHA-256 fingerprint: 3F:A2:...:9C
```

**In the browser of another device**, at the first connection: the warning
that the connection is not private. The person opens the details of the
certificate, compares the fingerprint with the one in the output, and
proceeds. The exact text of the procedure, with the screenshots, belongs to
the installation procedure.

**In the interface** nothing changes: the sentences of the Authentication
Specification about `TransportNotSecure` remain true and sufficient.

# Verification

| # | Commitment | Verification |
| --- | --- | --- |
| T1 | The interface is served by the engine | An address of the interface receives `index.html`; an existing file is served; an unknown `/api` receives `404` in the common structure, not the page |
| T2 | HTTP stays on the loopback | No HTTP listener on any address other than the loopback |
| T3 | The generated certificate has the right names and signs no other certificate | Names of the computer and of the interfaces present; use limited to the server; no authority capability |
| T4 | The private key is protected | The key file is readable only by the user running PIE |
| T5 | The certificate is renewed when it must be, and only then | Near expiry and with changed names: new. Otherwise: the same, with the same fingerprint |
| T6 | A certificate of one's own replaces the generated one | No generation; an unreadable or expired certificate: startup prevented with the reason |
| T7 | HSTS only with a certificate of one's own | Absent with the generated certificate, present with one's own |
| T8 | The names of the computer are accepted, others are not | `Host` with the name or the address of the computer: accepted. With a foreign name: `400`. `*`: startup prevented |
| T9 | An undeclared proxy does not make a request local | From the loopback with `X-Forwarded-For` and no trusted proxies: a password receives `TransportNotSecure` |
| T10 | A declared proxy conveys client and encryption | From a trusted proxy with `X-Forwarded-Proto: https`: password accepted, cookie `Secure`. From an untrusted address: headers ignored |
| T11 | A test in the field | From a phone on a home network: warning, fingerprint compared, signed in, domains read |

# Decisions Taken

For each, the alternative not chosen and its cost.

| # | Decision | Adopted | Alternative not chosen and its cost |
| --- | --- | --- | --- |
| **S1** | Default certificate | **Generated by PIE, for the server alone**; a browser warning once per device, a fingerprint to compare | *A local authority to install on the devices*: no warning, but installing it on a phone is difficult, and its key could sign a certificate for any site at all. *No default certificate*: no warning, but no access from the network until the operator obtains one |
| **S2** | HSTS | **Only with a certificate of one's own** | *Always*, as the Authentication Specification used to say: at the first renewal of the generated certificate the browser would no longer let anyone in |
| **S3** | Reachable from the network by default | **Yes**, HTTPS on every interface, `5443`; `0` closes it | *No, to be enabled*: more prudent, but it leaves the installation with the former limit until someone finds the setting |
| **S4** | Names accepted | **Also the name and addresses of the computer**, automatically | *Only those written in `AllowedHosts`*: the person would have to know and write the address of their own computer, which the router may change |
| **S5** | Interface | **Served by the engine**, same address | *A separate server for the interface*: two processes, two certificates or a proxy, and rules between different origins |
| **S6** | Local request with forwarding headers and no declared proxy | **Not local** | *Local*: a proxy configured in the clear would have passwords that travelled in the clear over the network accepted |
| **S7** | Validity and renewal | **397 days**, renewal 30 days before expiry or when names change | *Longer validity*: fewer warnings, but some systems, Apple's for instance, refuse certificates of longer duration |

# Known Limits

* **The browser warning.** A locally generated certificate is recognised by no
  browser. The person accepts it once per device, and again at every renewal
  or change of address. It is the price of an installation that depends on no
  external service. Whoever wants to avoid it supplies a certificate of their
  own.
* **The first connection trusts the person.** Against someone pretending to be
  PIE at the very first connection, the protection is the comparison of the
  fingerprint. If the person does not do it, a hostile device on the network
  can present a certificate of its own.
* **A changed address requires a restart.** The certificate and the names
  accepted are recomputed at startup, not while PIE is running.
* **The generated certificate covers the names the computer knows.** A name
  assigned by the router and unknown to the computer has to be added in
  `Transport:Names`.
